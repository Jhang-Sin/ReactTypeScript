檔案清單（此功能相關）

1) condition-config.js
存放 TIME_PERIOD、CONDITIONS 與 CONDITION_RULES（身分 × 時段 對應條件集合）。
2) condition-engine.js
實作 ConditionEngine 類別：提供 getConditions(userType, period)、checkCondition(...) 等方法，供所有頁面呼叫。
3) common/modal.js / modal.css
通用彈出視窗（或使用 SweetAlert2），提供 showConfirmModal(options)。所有需要提示／確認的位置都使用此模組。
4) reg_by_doctor.js / reg_by_date.js / reg_by_dep.js
各掛號頁面的業務邏輯：在按下「掛號」按鈕前呼叫 beforeRegister({doctorId,date,noon})，由該函式與 ConditionEngine 互動。
5) data/noon_type.json
時段代碼對照（01..04），頁面顯示中文值（上午/下午/...）。
6) data/schedule.json
醫師排班資料，欄位包含 doctorId, doctorName, department, items[]（每項含 date 與 noon 代碼）。
7) reg_list / localStorage
掛號成功後寫入的紀錄（目前為 localStorage.registrations 或可改成呼叫後端 API）。

未來新增角色 / 條件時的修改說明（步驟）

  1. 新增或修改條件集合（CONDITIONS）
    編輯 condition-config.js 裡的 CONDITIONS（例如新增 H）
  2. 新增或修改角色規則
    在 CONDITION_RULES 中新增角色（例如 Q6）或調整既有角色在不同時段對應的條件集合。
  3. 條件實作/邏輯函式
    若新增的條件（例如 H）需要具體判斷程式，請在 condition-engine.js 中新增對應的判斷方法或把檢核點委派給後端 API（適用較複雜或需即時查詢之條件）。
  4. 更新彈窗行為（若有新角色需不同按鈕）
    修改 modal.js 的配置或在呼叫時傳入不同的 option（type=alert/confirm/forceable 等）。
  5. 測試
    本機測試：在 localStorage 設定不同 userRole（例如 localStorage.setItem('userRole','Q4')），並測試上午/下午不同情境。

快速範例：beforeRegister() 節錄（整合呼叫）

// 假設 conditionEngine 與 showConfirmModal 已存在
async function beforeRegister({ doctorId, date, noon }) {
  const userType = localStorage.getItem('userRole') || 'Q1';
  const period = (noon === '01') ? '上午' : '下午';
  const needed = conditionEngine.getConditions(userType, period); // e.g. ['A','B','C']

  // 檢核每一條件（示範為同步 checkCondition）
  const failed = needed.find(cond => !conditionEngine.checkCondition(userType, period, cond));

  if (!failed) {
    doRegister(doctorId, date, noon);
    return;
  }

  // 有未通過條件
  if (['Q1','Q2','Q3'].includes(userType) && period === '上午') {
    showConfirmModal({ title: '掛號失敗', message: '此醫師已達掛號上限。', type: 'alert' });
    return;
  }

  // Q4/Q5 或醫師/管理者等可強制掛號
  showConfirmModal({
    title: '條件未通過',
    message: '已達掛號上限，是否仍要繼續掛號？',
    type: 'confirm',
    onConfirm: () => doRegister(doctorId, date, noon)
  });
}
提示：實務中 checkCondition 有些可能需呼叫後端（例如查詢實際名額是否已滿），請把該檢核設為 async，ConditionEngine 可回傳 Promise。

最後備註

  • 把 condition-config.js 視作「業務規則配置檔」，建議透過版本管理（git）與註解維護。
  • 若條件日後會由後端統一管理，可把 condition-config 轉為 API 並由後端回傳規則。
  • 彈窗建議使用 SweetAlert2（外觀佳、易用），或自行用 modal.js 建一套符合 HIS 風格的共用模組。
