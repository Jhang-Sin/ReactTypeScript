

# HIS－排班排程作業｜開發對話開場

我目前正在 HIS 專案中開發「排班排程作業」。

這個功能不是從零開始，目前已經完成：

* 基本頁面展示
* 基本資料載入
* 基本互動操作
* Vue 3 基礎綁定
* 排班資料的基本呈現
* 基本操作流程已經可以運作

因此，這篇對話的重點不是重新設計整個架構，而是：

> **在目前已經可以運作的基礎上，逐步深化「排班排程作業」的業務功能與模組化程度。**

---

## 一、目前 HIS 專案的基本開發原則

我希望延續目前 HIS 專案已經建立的開發方式：

1. Single Source of Truth
2. Guarded Flow
3. Operational Visibility
4. User Visual Feedback
5. Decoupling
6. 完整模組邊界

也就是：

* 共用功能集中管理
* 不重複實作相同工具
* 每個模組有自己的責任範圍
* UI、資料處理、業務邏輯盡量分離
* 發生問題時可以清楚知道是哪一層出錯
* 使用者操作時要有明確的視覺回饋

## 二、目前技術環境

目前 HIS 專案使用：

* Vanilla JS
* Vue 3
* TypeScript（專案其他部分）
* JSON 作為目前模擬資料來源
* GitHub Pages 作為目前展示環境

Vue 目前使用本地版本：

```html
<script src="../../common/js/vue.global.prod.js"></script>
```

不使用 CDN Vue。

---

## 三、目前共用工具

共用工具主要集中在：

```text
HIS/common/js/
```

其中重要工具：

* `utilities.js`
* `modal.js`
* 其他共用 Engine / Utility

其中：

```js
HIS.util.loadJSON(...)
```

是目前主要的 JSON 資料讀取方式。

### 重要原則

路徑判斷由 `utilities.js` 統一處理。

頁面或功能 JS：

* 不自行處理 GitHub Pages `/ReactTypeScript/HIS`
* 不重複加入 BASE / ROOT
* 不大量使用 `../`
* 不自行複製一套路徑判斷邏輯

也就是：

> **Path 的 Single Source of Truth 是 utilities.js。**

---

## 四、資料架構

目前資料仍以 JSON 模擬資料庫：

```text
HIS/DB/
```

排班相關資料主要包含：

* `schedule.json`
* `doctors.json`
* `doctors2.json`
* `departments.json`
* `depcode.json`
* `dep_map.json`
* `noon_type.json`

其中 `schedule.json` 是排班核心資料。

目前已建立的概念：

### schedule

* `schedule_NO`

  * 排班資料流水號
  * Primary Key

* `doctorId`

  * 醫師代碼

* `depCode`

  * 科別代碼

* `date`

  * 看診日期
  * 格式為 `YYYY-MM-DD`

* `noon`

  * 午別 / 診次代碼
  * 對應 `noon_type`

* `status`

  * `1 = 有效`
  * `0 = 無效`

### noon_type

* `noon`

  * 午別代碼

* `value`

  * 畫面中文顯示名稱

* `time`

  * 診次 / 開診時間

其中：

> `noon_type.value` 是前端畫面顯示用的中文名稱。

## 五、日期處理規則

HIS 核心業務日期統一使用：

```text
YYYY-MM-DD
```

目前不要把 HIS 業務日期直接轉成：

```js
new Date("YYYY-MM-DD")
```

日期比較以字串方式處理。

例如：

```js
"2026-08-20" < "2026-08-21"
```

可以直接進行日期先後比較。

`Date` 主要保留給：

* 今天日期計算
* 日期加減
* 到期時間
* 倒數
* 真正的時間點運算

## 六、Vue 開發習慣

目前 Vue 頁面偏向：

```js
(() => {

    const app = Vue.createApp({
        data() {
            return {
                // 安全初始值
                dataList: [],
                schema: {},
                errorMsg: ""
            };
        },

        methods: {
            // ...
        },

        mounted() {
            // init
        }
    });

    window.__vue_app__ = app;

    app.mount("#app");

})();
```

希望維持：

* IIFE 避免全域污染
* 陣列初始值使用 `[]`
* 物件初始值使用 `{}`
* 必要時使用 `Array.isArray()`
* 不混用 Vue 控制 DOM 與大量原生 DOM 操作
* UI 儘量使用 Vue template / binding / event

# 七、目前排班排程作業的開發狀態

目前：

> **基本展示與互動功能已完成。**

因此後續開發請以「現有程式碼為基礎增量修改」為原則。

不要在沒有必要的情況下：

* 重寫整個頁面
* 重建既有架構
* 新增 Loader
* 新增 Router
* 新增過度抽象的 Service
* 把已經可以運作的功能重新設計

如果目前架構已經足夠，優先：

> **最小必要修改（Minimal Necessary Change）**

# 八、排班模組的核心設計觀念

排班不是單純「顯示 JSON」。

它應逐漸形成：

```text
排班資料
   ↓
排班規則
   ↓
排班狀態
   ↓
畫面操作
   ↓
資料異動
```

後續可能會逐步處理：

* 日期
* 醫師
* 科別
* 午別
* 診次
* 排班建立
* 排班修改
* 排班停用
* 排班恢復
* 排班查詢
* 排班衝突
* 排班有效性
* 排班資料驗證

但請不要一次把所有功能全部做完。

希望採：

> **一個功能 → 驗證 → 穩定 → 再增加下一個功能**

---

# 九、資料與業務邏輯的責任

希望維持：

```text
UI
 ↓
功能 JS
 ↓
共用 Utility / Engine / Service（需要時）
 ↓
JSON / 未來 API
```

但是不要為了形式而增加 Service。

如果目前功能只需要：

```js
HIS.util.loadJSON(...)
```

即可完成，就先使用既有 Utility。

只有當：

* 多個頁面重複使用相同資料處理
* API 存取開始複雜
* 商業邏輯需要集中
* 資料轉換需要共用

才考慮抽出 Service / Engine。

# 十、排班功能開發方式

後續每增加一項功能，希望按照：

### ① 先說明「這個功能負責什麼」

### ② 說明資料流

例如：

```text
使用者選擇日期
↓
取得排班資料
↓
篩選日期
↓
篩選有效資料
↓
取得醫師 / 科別 / 午別資訊
↓
組合畫面資料
↓
Vue 綁定
```

### ③ 再決定程式放在哪裡

不要先寫程式再想責任歸屬。

### ④ 優先沿用現有模組

能使用既有：

* utilities
* modal
* schedule engine
* condition engine
* calendar

就不要重新寫一份相同功能。
